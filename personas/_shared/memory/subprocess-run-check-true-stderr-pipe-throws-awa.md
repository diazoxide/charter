subprocess.run(check=True, stderr=PIPE) THROWS AWAY THE DIAGNOSIS IT LOOKS LIKE IT IS COLLECTING. CalledProcessError.__str__ is the argv and the exit status and nothing else — the piped stderr is attached to the exception object and never printed. So a command that failed FOR A STATED REASON surfaces as a command that merely failed. charter had this in tools/sweep.py Sandbox.__init__ and it cost hours: an intermittent CI red read as `git clone ... exited 128` with no cause, and I guessed a shared-temp-path race (the #893/#894 shape) that was disproved by 1600 concurrent iterations with zero failures. The real cause was ENOSPC, reproduced character-for-character on a 20 MiB filesystem with 250 KiB free, and git had said so all along in the stderr that was collected and dropped. Either pass the captured stderr into the raised error, or do not capture it and let it reach the terminal. Second lesson from the same fix: give a machine failure its own exception category, distinct from a verdict about the code — nothing had been measured when the sandbox failed to build, so reporting it as a sweep-gate failure was a false statement about the branch.
