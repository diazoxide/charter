# A guard that ends a heredoc body EARLIER than bash does is NOT automatic

_2026-09-11 16:15 · persistent_

A guard that ends a heredoc body EARLIER than bash does is NOT automatically safe; the opposite was assumed in the chat-handoff Task 4 brief (item E) and in a PR 972 review. With TWO heredocs on one command, the text after a too-early end is consumed as the NEXT heredoc's body. If that next heredoc feeds a reader such as cat, its body is stripped as data, so a line bash actually executes vanishes from the guard. Measured by PR 974's implementer on 2026-09-11 in bash, zsh and dash with a planted fake secret. The shape is a bash heredoc with delimiter A, joined by && to a cat heredoc with delimiter B. In the first case, a body line holding a space then A, which bash does not treat as the terminator, made charter's lenient strip-then-compare match end the body early. In the second, an unquoted body line ending in a backslash joins the next line in bash. Both ran the secret while the guard allowed them, and main denied both. Rule for charter's heredoc handling: match terminators exactly as the shell does (no stripping, except that <<- strips leading TABS only, never spaces); honour backslash-newline only in UNQUOTED bodies; and test every terminator edge against real shells before claiming a direction is safe.
