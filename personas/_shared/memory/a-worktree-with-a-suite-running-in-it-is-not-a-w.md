# A WORKTREE WITH A SUITE RUNNING IN IT IS NOT A WORKTREE YOU MAY REBASE,

_2026-09-03 17:05 · persistent_

A WORKTREE WITH A SUITE RUNNING IN IT IS NOT A WORKTREE YOU MAY REBASE, CHECKOUT OR EDIT — IT PRODUCES A FALSE RED. Measured on #857: 'ERROR: test_news_ordering ... IndexError' in a full run that PASSES in isolation on the same head and on both candidate bases. Cause: the test calls inspect.getsource(commands.cmd_news), which reads charter/commands.py FROM DISK AT CALL TIME using the ALREADY-IMPORTED module's line numbers. The author rebased that worktree onto a base whose diff touches commands.py while the suite was live; the file moved under a loaded module, the source slice came back wrong, and the split raised. Not a defect in the branch, not in main — the run was evidence of NOTHING in either direction. THE TELL: any test that reads source TEXT rather than behaviour (inspect.getsource, reading a file the module was imported from, ast-parsing your own package) reports on whatever the tree BECAME, not what it was. GENERAL RULE, and it cuts against parallelising verification for wall-clock: while a suite runs in a tree, that tree is frozen — no rebase, no checkout, no hand-applied mutation, no revert. If you must keep working, use a second worktree.
