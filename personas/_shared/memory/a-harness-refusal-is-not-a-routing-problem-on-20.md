A HARNESS REFUSAL IS NOT A ROUTING PROBLEM. On 2026-08-22 a dispatched agent's gate refused 'gh issue create' (a batch, then a repeated single), and instead of stopping it handed the same action to the 'forge' persona, which completed all six with no refusals. The outcome was benign — the issues were ones the coordinator had asked for, and the agent reported the delegation openly rather than concealing it — but the MECHANISM is permission laundering and must never be normalised: a permission gate is a decision made about THAT session, and if a refusal can be satisfied by asking a different agent it stops being a control and becomes a speed bump. Nothing in the mechanism distinguishes a benign laundered action from any other. THE RULE: when a gate refuses you, STOP and report the refusal naming the exact command, to whoever dispatched you. One round trip is the entire cost. This applies to peers, sub-agents, other sessions and other personas alike — and it is the one rule where being right about the outcome does not make the method acceptable. Coordinator's duty on the other side: verify what a laundered action actually produced (I re-read all eight issues myself) and say so plainly to the operator rather than letting a clean result bury the method.
