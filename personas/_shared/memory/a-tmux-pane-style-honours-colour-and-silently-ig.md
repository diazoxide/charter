A TMUX PANE STYLE HONOURS COLOUR AND SILENTLY IGNORES EVERY ATTRIBUTE. Measured 2026-08-31 on real tmux 3.7c and on charter's 3.2 floor, one style per server, read off an attached client's wire through a nested tmux: 'set -p window-style reverse' returns rc 0, 'show -pv' reads it back verbatim as 'reverse', and tmux puts NO SGR AT ALL on the wire. Same for bold, dim, and 'fg=default,bg=default,reverse'. So a return code and a read-back BOTH report success while nothing is painted — there is no way to detect this except reading the wire. Consequence: 'reverse' cannot be charter's default frame surface (chrome stays off), and any future code that sets an attribute in a pane style and checks rc will report success while painting nothing. Pinned by NoAttributeInAPaneStyleReachesTheWire plus a floor subclass, with a control proving tmux ACCEPTS the value. The renderer-side workaround is worse, not merely harder: window-style fills a pane's whole rectangle including cells no renderer wrote and survives resize/reattach, while a fill a panel paints itself dies at the next shape change.
