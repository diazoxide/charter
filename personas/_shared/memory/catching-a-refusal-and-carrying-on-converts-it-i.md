CATCHING A REFUSAL AND CARRYING ON CONVERTS IT INTO A SILENT PERMIT. charter had a plane format check from the beginning: instance.SCHEMA in charter.toml, stamped by init, and instance.load RAISED on a version from the future. It never refused anything, because config.derive caught that exception, recorded CONFIG_ERROR and continued with cfg = {}. Every command then operated on a plane charter had just been told it could not read. The sharpest instance: known_forges_report received the refusal and returned an EMPTY FORGE SET — a PreToolUse guard that looks present and denies nothing. Nobody had hit it only because nobody had yet opened a plane written by a newer charter. Fixed in #914 by splitting PLANE_REFUSAL from CONFIG_ERROR and having cli.main decline (doctor/version/update exempt, init/reinit/hook NOT). The general rule: when a check raises to say "you may not proceed", the handler that swallows it must either propagate or deny — a default-empty value in a security path is failing OPEN. Grep for except blocks that turn a raised refusal into a falsy default and ask what reads that default.
