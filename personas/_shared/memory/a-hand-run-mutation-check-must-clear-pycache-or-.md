# A HAND-RUN MUTATION CHECK MUST CLEAR __pycache__ OR IT MEASURES THE UNMU

_2026-09-03 15:31 · persistent_

A HAND-RUN MUTATION CHECK MUST CLEAR __pycache__ OR IT MEASURES THE UNMUTATED TREE — STALE .pyc GIVES FALSE KILLS. Measured on #849: an EQUAL-LENGTH mutation applied and reverted inside one second leaves a .pyc with the SAME mtime and SAME size, so CPython's import check (mtime+size, not content) reuses it and the test runs the ORIGINAL bytecode. CORRECTION, from a second agent that pushed back: the DIRECTION depends on which way the cache is stale, and both are possible. Applying a mutation over a cached ORIGINAL runs the original -> test passes -> FALSE SURVIVOR. Reverting a mutation over a cached MUTATED build runs the mutant -> test fails -> FALSE KILL. The first agent reported four false KILLs (the revert direction); the second argued a stale .pyc 'mechanically cannot' manufacture a kill, which is true only of the apply direction. Clear the cache on BOTH transitions, not just before the run. This is the standard way agents verify a survivor by hand ('apply the mutation, run the test, see it red, revert') and it is silently wrong for any same-length edit — swapping an operator, strip->lstrip, <= to <, True to False are all equal-length. Rule: 'find . -name __pycache__ -prune -exec rm -rf {} +' (or PYTHONDONTWRITEBYTECODE=1) between applying a mutation and running the test, EVERY time; and prefer sleeping past the mtime granularity is NOT enough because size matching alone is not the check — clear the cache. Same false-green family as [[macos-has-no-timeout-command-and-the-failure-is-]] and [[local-green-can-lie-because-the-test-loader-diff]]: the harness around the suite lied, not the suite.
