A FRESH CHAT ID IS NOT A FRESH CHAT NAME — ordinals are recycled, so "we mint a new id" does not protect you from stale per-id state. Established 2026-09-01 while building quit/reopen. new_chat_id counts UP FROM 1 and reap FREES the ordinals a quit dead chats held, so a reopened chat VERY OFTEN GETS THE SAME NAME BACK (alpha.1 quits, alpha.1 reopens). Any state keyed on the chat id and living OUTSIDE the frame directory therefore survives into a different conversation: .charter/sessions/<fid>.workspace, .lock, and anything else under sessions/. That is #731, and while the per-session pointer was a membership rung of state.own_workspace it was worse than marginal — a charter workspace use gamma typed in the OLD alpha.1 would decide the NEW alpha.1 membership, outranking both the reopen manifest and the launcher own record_workspace. #794 removed that rung and it is now pinned by a test that PLANTS the stale pointer and is verified red with the rung restored. TWO RULES. (1) When an id can be recycled, "mint a new id" is not isolation — the isolating act is REAPING THE STATE KEYED ON THE OLD ONE, which is what #731 still asks for (the lock half survives). (2) When you argue a hazard is marginal because ids differ, CHECK WHETHER THE ID SPACE IS DENSE AND REUSED — I reported this one as "can still bite via ordinal recycling" before realising recycling is the COMMON case, not the edge.
