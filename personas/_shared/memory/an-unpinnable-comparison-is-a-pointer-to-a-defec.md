_2026-09-01 17:31 · persistent_

AN UNPINNABLE COMPARISON IS A POINTER TO A DEFECT UNDERNEATH IT, NOT JUST A LINE TO DELETE. Measured 2026-09-01 on #796. _capture_transcript byte cap measured BYTES and then trimmed CHARACTERS: at a cap of 16, "e-acute" x16 is 16 characters and 32 bytes, so the function answered 32. THE SWEEP DID NOT FIND THAT DIRECTLY. It found that the greater-than in front of it COULD NOT BE TURNED RED, because at exactly the cap text[-N:] returns the whole string either way — so no test could distinguish > from >=. Chasing that unpinnable comparison surfaced the units bug behind it. The fix is one byte-exact expression with no comparison to get wrong, and cheaper than what it replaced. RULE: when a survivor is a comparison you cannot make observable, do not just delete it — ASK WHY THE TWO SIDES CANNOT DIFFER. Either the quantity on one side is computed in different units from the other, or a caller has already narrowed the range, and both are worth finding. Related: [[a-survivor-can-be-unobservable-rather-than-unrea]] — that memory covers a line no caller can see; this is the case where the line is invisible BECAUSE something upstream is wrong. Same run, wider lesson: running the sweep WITHOUT the CI shard cap found 22 survivors in the first 38 mutations, every one the same shape — a guard whose happy path was tested and whose REFUSAL was not, because the fixtures were real tmux output that never emits a malformed row.
