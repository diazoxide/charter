# AN UNANSWERED QUERY THAT READS AS ZERO IS A FALSE GREEN YOU BUILT YOURSE

_2026-09-03 17:33 · persistent_

AN UNANSWERED QUERY THAT READS AS ZERO IS A FALSE GREEN YOU BUILT YOURSELF — I SHIPPED ONE THREE TIMES. My CI-watching monitors counted pending checks with: c=$(gh api .../check-runs -q '[.check_runs[]|select(.status!="completed")]|length' 2>/dev/null || echo 1); pend=$((pend + c)). When gh exits 0 with EMPTY output — which it did repeatedly, alongside a recurring 'expected an object but got: array ([])' — c is empty, $((pend + )) evaluates to pend, and an UNANSWERED query is indistinguishable from 'nothing pending'. The monitor announced ALL SETTLED three separate times while a 'Sweep shard 1 of 1' was in_progress; '|| echo 1' does not help because the failure mode is exit 0 with no body, not a non-zero exit. FIXES, all three needed: (1) validate the response is a NUMBER ('case $x in ''|*[!0-9]*) treat as pending;;') rather than trusting arithmetic on it; (2) sanity-check a TOTAL alongside the filtered count — a check-run list with fewer than ~5 entries on this repo means the answer is incomplete, not that the work is done; (3) require N consecutive quiet passes, because a re-push leaves a real window where nothing is in flight yet. GENERAL RULE: in any polling loop, 'no results' and 'no remaining work' must be different branches. Silence is not success — the same sentence the Monitor tool's own documentation uses about filters, applied to the counter instead of the filter.
