A NEW BRANCH THAT ACCEPTS A SUPERSET OF A NEIGHBOURING GUARD'S INPUTS UNPINS THAT GUARD, and a hand mutation check of only the new branch cannot see it (PR 970, 2026-09-11). The local sweep at 3624287 pinned guardseen.folder_standing's 'if not harness and source != PLUGIN' (unnamed sighting -> unknown). 537d0fc then added 'if source != PLUGIN and _registry.get(harness) is None' (unregistered name -> unknown) right after it. registry.get(None) is also None, so with the unnamed block deleted, unnamed sightings fell into the new block. The unnamed test's assertions ('cannot tell which harness', 'CHARTER_HARNESS' in the hint) matched that block too, and CI's sweep on 537d0fc reported the OLD guard as its one unpinned survivor. My hand check (M0) had only deleted the new branch. Rules: (1) when adding a branch, hand-mutate every neighbouring guard whose inputs it also accepts; (2) pin what makes each branch's output distinct ('names no harness' versus 'names None'), not the sentence they share; (3) read CI's sweep gate on the pushed head even after a local sweep, because it sweeps the final diff.
