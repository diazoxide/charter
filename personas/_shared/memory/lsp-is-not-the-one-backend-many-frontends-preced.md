# LSP IS NOT THE ONE-BACKEND-MANY-FRONTENDS PRECEDENT, AND GIT DOES NOT SA

_2026-09-05 22:53 · persistent_

LSP IS NOT THE ONE-BACKEND-MANY-FRONTENDS PRECEDENT, AND GIT DOES NOT SAY ITS FILES ARE ITS API. Both were premises I asserted and primary sources refuted (docs/research/2026-09-05-interface-agnostic-cores.md). LSP spec, verbatim: "The protocol currently assumes that one server serves one tool. There is currently no support in the protocol to share one server between different tools" — open since 2020, still no plans as of May 2026. LSP solved M x N in IMPLEMENTATIONS, not concurrent clients; tmux and Kubernetes are the real precedents for many simultaneous clients. git(1) points alternative front ends at the PLUMBING COMMANDS, whose "input, output, set of options and the semantics are meant to be a lot more stable" — the only thing git says to a program reading .git/ directly is a rule for REFUSING (unknown core.repositoryformatversion means "MUST NOT operate on that repository"). packed-refs is specified only in C, and gitoxide shipped subtly wrong refs for years because git rtrims on read. So "the files are the API" is respectable about where TRUTH lives (Maildir, jj op log) and a mistake about INTERFACE. Also: jj never refused a daemon, it plans one, because its library seam leaked.
