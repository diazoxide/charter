A NO-OP tmux WRITE STILL REPAINTS THE WHOLE CLIENT — THE COST IS THE COMMAND LIST, NOT THE CHANGE. Measured on #866 with a real pty client on 3.7c and the 3.2 floor: "resize-pane -x 22" on a pane ALREADY 22 wide sends 1672 bytes (3.7c) / 1811 (3.2) to the client, byte-identical to a real resize. Three such commands in ONE list send one of those; a pure read ("display-message -p") sends 0. So tmux redraws the client ONCE PER WRITE-CARRYING COMMAND LIST, whether or not anything changed. CORRECTION TO WHAT I TOLD FIVE AGENTS: I attributed the switch blink to the harness TUI reflowing four times. It does not. The arriving harness pane gets exactly ONE SIGWINCH (the four split-windows in their single list) and the three resize-pane lists after it deliver ZERO, because resizing a pane to the size it already has is a true no-op FOR SIGWINCH. Both facts are true and they measure different things: SIGWINCH follows actual geometry change, client repaint follows the LIST. To reduce flicker, count write-carrying LISTS — not resizes, not round trips. Also measured there: on attach tmux withholds a repaint until its terminal-feature query times out, about 5 seconds against a pty that never answers (bursts at 6ms and 5006ms, nothing between), and inside that window the first command of any kind flushes it — so a read drawing 0 bytes on a settled client draws 617 at one second, which flaked a test until the fixture waited it out.
