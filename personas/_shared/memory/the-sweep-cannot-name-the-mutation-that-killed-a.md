# THE SWEEP CANNOT NAME THE MUTATION THAT KILLED A RUNNER, AND THIS IS NEW

_2026-08-31 01:37 · persistent_

THE SWEEP CANNOT NAME THE MUTATION THAT KILLED A RUNNER, AND THIS IS NEW BEHAVIOUR TO BUILD, NOT INFORMATION BEING DROPPED. Verified 2026-08-31 by the #754 author rather than taken on relay: run_one logs AFTER decide returns, and --json is written once at the end, so the mutation that consumed its runner is precisely the one with NO line in the report — and an OOM-kill is byte-identical to a spot reclaim (both exit 143). Separately measured on the #710 branch: FOUR of 118 mutations do not terminate, the worst allocating ~3.8 GB/min, which exhausts a GitHub runner in 2-4 minutes. So a shard dying is a real diagnosis, not automatically flakiness. #630 closed the hanging-mutation hole with a per-mutation timeout and A TIMEOUT CANNOT SAVE A RUNNER THAT HAS BEEN CONSUMED — the timer and the process die together. Two traps when analysing this: shard_of is plan[index-1::count] ROUND-ROBIN over a plan whose length changes between commits, so 'shard N' is not a stable subset across runs; and Mutation.tag is line-keyed, so ANY runaway-to-shard map is valid only against the exact swept commit (one agent built a convincing map against its dirty working tree and had to retract it).
