CORRECTION — 'A FORCE-PUSH FIRES NO SYNCHRONIZE EVENT' IS TOO STRONG; THE #646 HOLE IS INTERMITTENT. I told five agents on 2026-08-31 that a force-push reliably fires no synchronize, so the sweep never re-runs and a stale green sits on the new head. Refuted by measurement: after one agent's rebase+force-push, head f59fb90 carried BOTH a workflow_dispatch sweep run AND a pull_request-event sweep run, plus tests runs from both push and pull_request. #646's own report ('two pushes produced no synchronize event') is real but describes an INTERMITTENT failure, not a rule. Do not rely on it in EITHER direction — neither 'force-push means no sweep' nor 'the checks I see must be current'. THE RELIABLE CHECK IS STRUCTURAL, and it already exists: 'Add up what the shards found' is a REQUIRED status check on main (#561, closing #646), so a sweep that never ran leaves the row MISSING and the PR reads BLOCKED rather than CLEAN. So: verify the check-runs are attached to the CURRENT head SHA, and trust the required-check to block a missing sweep. Note also sweep.yml's header: adding 'push:' would WIDEN the hole, because pull_request and push sweep different trees (pull_request uses the merge commit and the PR base sha; push has no BASE_SHA and charges the branch tip against merge-base), so a push-scoped run of a different tree would satisfy the required check meant for the PR-scoped one.
