Stamping news entries ACTIVATES their 'check:' probes, and that makes a release the moment a bad probe goes live. 'charter doctor' runs every RELEASED entry's check: in-process via news._dispatch (which calls the cli func directly, not a subprocess), so an entry whose check: is 'doctor' re-enters doctor.check_news_adoption without bound — each level doing a full ~2s check sweep, so it never terminates in practice. While the entry sits at 'version: unreleased' the probe never runs, so the landmine is INVISIBLE on main and arms itself at 'charter news stamp'. Found preparing 0.47.0: docs/news/<v>-plugin-behind-names-handlers.md (from #307) carried 'check: doctor'; after stamping, 'charter doctor', 'charter doctor --json' and 'charter news --pending' all hung, while 'charter news --for <v>' (0.1s) and the tag/version guard both PASSED — so CI's guard job would NOT have caught it; only the 'test' job would, after burning a tag. Fix was to delete the check: line (the entry's own text said 'Nothing to adopt', so INFORMATIONAL was always correct). ALWAYS run 'charter doctor' and 'charter news --pending' with a timeout immediately AFTER stamping, never only before. The durable defect — _dispatch has no re-entrancy guard, so any future 'check: doctor' rebricks it — is upstream and should be filed, not patched around.
