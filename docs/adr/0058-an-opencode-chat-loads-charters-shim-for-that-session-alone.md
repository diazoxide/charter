# An opencode chat loads charter's shim for that session alone

**Accepted 2026-09-26**, for charter#371.

Until this, the app refused an opencode profile ("charter-app v1 starts Claude Code and Codex,
and opencode follows", spec decision 6). The retired Python charter had run opencode with every
guard through a shim it wrote into `~/.config/opencode/plugin/`. This record is how the app
starts opencode instead, and what that can and cannot guarantee. It is the third adapter behind
the same seams as the other two, so opencode is one arm of `harness::Harness`, one
`harness_plugin` adapter and one `plugin_install` adapter, not special cases.

## Measured

On opencode 1.18.23, with a throwaway `HOME` and a stand-in OpenAI-compatible model that asked
for one `bash` call and logged every request it received.

- **A plugin can be loaded for one process, with nothing written.**
  `OPENCODE_CONFIG_CONTENT='{"plugin":["file://<path>"]}'` loaded the script at `<path>`.
  opencode concatenates the `plugin` lists of every config, so the global plugin directory's
  scripts loaded beside it. A project `opencode.json` holding `"plugin": []` did not remove it.
  A bare path, a `file://` URL with a raw space and a percent-encoded one all loaded.
- **Throwing from `tool.execute.before` refuses the call.** The tool did not run, and the
  model's next request carried the thrown message as the tool's result. The plane's vault file
  never reached it.
- **`--pure`, `OPENCODE_PURE=1` and `OPENCODE_PURE=true` load no external plugin**, and with any
  of them the vault's content reached the model. `--pure` sets `OPENCODE_PURE=1` inside opencode
  before plugins load, so nothing in the environment can undo it.
- **The signals.** `chat.message` fires once per prompt, before the model is asked. A text part
  pushed onto its `parts` reached the model inside the user message. The `event` hook sees
  `session.created` (with `info.parentID` on a sub-agent's session), `session.idle` when a turn
  ends, and `permission.asked` exactly when the TUI showed "Permission required", followed by
  `permission.replied`. In the TUI a session is created at the first prompt, not at launch.
  Quitting fired no event and ran no `exit` handler in the plugin.
- Tool ids and arguments, as opencode sent them to the model: `bash {command, timeout,
  workdir}`, `read {filePath, …}`, `grep`, `glob`, `write`, `edit`, `task`, `skill`,
  `todowrite`, `webfetch`.

End to end, through the real `charter` and the generated shim (see below), a `bash` call that
read `.charter/vaults/db.json` in a plane was refused by the guard, and the model got the
refusal instead of the file.

## The decision

**The bundle ships a shim, and each opencode chat the app starts loads it through
`OPENCODE_CONFIG_CONTENT`.** The shim is `plugin/opencode/charter.ts`, beside the Claude Code
plugin's own directories, which Claude Code does not read. It is generated by
`charter_core::opencode::shim`, and the bundled file is that output byte for byte, which a test
checks, as it does for `hooks/hooks.json`. The chat's environment carries
`OPENCODE_CONFIG_CONTENT` naming the shim, `CHARTER_HOOK_BINARY` naming the app's `charter`, and
`OPENCODE_PURE=0`. Nothing goes on the command line, and nothing is written.

**The shim carries no policy.** It forwards each event to `charter hook <word>`, with the payload
a Claude Code hook would get, and turns the answer into opencode's terms.

| opencode | `charter hook` | What the answer does |
|---|---|---|
| `tool.execute.before` | the tool's pre-hook, by Claude Code's name for it (`bash`→`pretooluse`, `read`/`grep`→`pretooluse-read`, `write`/`edit`→`pretooluse-edit`, `task`→`pretooluse-dispatch`), every other tool → `pretooluse` | a `deny`, exit 2 or no answer throws, which refuses the call |
| `tool.execute.after` | `posttooluse`, `posttooluse-skill`, `posttooluse-dispatch` | a note is appended, fenced, only to `bash`/`edit`/`write` output |
| `chat.message`, a session's first | `sessionstart` (`source` `startup`, or `resume` for a session this process did not create) | its context rides the prompt as one more text part |
| `chat.message` | `userpromptsubmit` | the same, so handed-back reports reach the chat |
| `session.idle` | `stop` | reported to the app |
| `permission.asked` | `notification` | reported to the app: the chat needs you |
| `shell.env` | none | `CHARTER_SESSION_ID` in every shell, as Claude Code's `CLAUDE_CODE_SESSION_ID` |

The routing table is the core's (`opencode::TOOLS`), and a test holds that every word a tool is
sent to is wired to that tool's Claude Code name in `hookreg`. A bash call is judged in its
`workdir`, where it will run. A sub-agent's session is followed to its parent. Its question is
the chat's, while its prompts and its idle are not.

**A guard that cannot answer does not allow.** A `charter` that is missing, crashed, timed out
or printed something unreadable refuses the tool call. Claude Code would let a hook that cannot
start through. The shim is charter's own code, so it takes the stricter side, the same side
charter's own guard takes when it crashes (#349). A `permissionDecision` of `ask` is allowed,
as the Python shim allowed it: opencode's plugin API has no way to ask. Those answers are
charter's routing nudges and never its refusals.

**The session.** opencode takes no id for a new session, so charter chooses none
(`chooses_session_id` is false) and adopts the first id the shim reports, as it does for Codex.
`opencode -s <id>` resumes. A later id from the same chat is ignored, including one from
`/new`, because opencode names no process variable to tell `/new` from a nested opencode.

**What a chat cannot report, said on the chat.** It reports nothing before the first prompt,
and nothing when opencode quits: the app sees the process end. After the operator answers a
permission prompt, the chat reads *waiting* until the turn ends. Only `userpromptsubmit` could
put it back to running, and that call hands the chat its queued reports.

**A profile that would load no plugin is not started.** An opencode profile whose command passes
`--pure`, or whose `env` sets `OPENCODE_PURE` or `OPENCODE_CONFIG_CONTENT`, is refused by
`wiring::refusal` before it is approved, with the reason. A wrapper script that adds `--pure`
itself cannot be seen, as with every other flag a wrapper adds.

**Plugin choice stays *not supported yet*** (ADR 0050). opencode loads every plugin from every
config and plugin directory together, and none of them can be turned off for one session.

## `charter plugin install --harness opencode`

ADR 0057's third adapter. It writes the shim's **guard-only** variant to
`$XDG_CONFIG_HOME/opencode/plugin/charter.ts`, else `~/.config/opencode/plugin/charter.ts`, with
this `charter` named by absolute path, because nothing outside the app sets
`CHARTER_HOOK_BINARY`. It installs the guard alone for Codex's reason. An app chat loads it too,
beside the bundled shim. A doubled guard only refuses twice, while doubled state hooks would
report every event twice and brief the chat twice.

The file's first line marks it as charter's. A file already at that name is replaced only when
charter wrote it: this command's, or the retired Python charter's shim (`// charter-version:`),
which `charter doctor` reports as superseded until then. Any other file there is left alone,
with a sentence. `uninstall` removes only charter's file. Run with no `--harness`, the command
skips opencode where its config folder does not exist, as for the other two.

## What this cannot guarantee

opencode imports every plugin into one JavaScript realm: the global plugin directory, a project's
`.opencode/plugin/`, and npm packages any config names. A plugin beside the shim can replace the
globals the shim calls. The shim takes its own references to the few it uses when it loads,
which stops a plain later monkey-patch and not a determined one. This is the limit the Python
charter's `foreign_plugins` named. It is the same class as a project `.claude/settings.json`
that runs its own hook: a file a chat can write that runs code at the next start. charter
reports what else opencode loads (the settings tab's harness-plugin list, `charter doctor`'s
`superseded plugin` row for the Python shim) rather than claiming a containment it does not
have. Guard rails, not guarantees.

## What was rejected

- **Writing the shim into `~/.config/opencode` for app chats**, as the Python charter did. It
  would change every opencode the operator runs, and ADR 0050 keeps chat launches from writing
  harness config.
- **`OPENCODE_CONFIG_DIR`, or `OPENCODE_CONFIG` pointing at a file.** Either would work. A
  directory or a file would have to exist somewhere per chat, or be shared and kept current. The
  whole config fits in a variable.
- **Failing open, as the Python shim did** ("a guard that cannot run must not block the
  session"). In the app the binary is the app's own, so a guard that cannot answer is a fault
  worth seeing, not a state to live in.
- **Mapping `permission.replied` to `userpromptsubmit`** to clear *waiting*. That hook takes the
  chat's queued handback reports, and the shim would then deliver them in the middle of a turn
  or drop them.
