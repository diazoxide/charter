---
version: 0.61.1
headline: `charter workspace rename` relinks the worktrees it moves, so git stops calling them prunable
---

A linked worktree and its clone point at each other by absolute path: the worktree's `.git`
file names the clone's admin directory, and that directory's `gitdir` names the worktree.
`charter workspace rename` moved both under the new name and rewrote neither link. Right
after the rename, `git worktree list` run from the clone called a live piece `prunable`,
`charter worktree list` answered `No worktrees.`, and a `git worktree prune` or `git gc` in
that clone deleted the piece's record while it could still hold uncommitted work.

Now the rename runs `git worktree repair` from every moved clone that has linked worktrees,
then asks git to read each link back in both directions. This covers pieces under
`.worktrees/`, worktrees you made by hand inside the workspace, and a worktree outside the
workspace. That one did not move, but its `.git` file still named the clone's old place, so
git run inside it failed.

A worktree git still cannot follow after the repair gets its own line with the command that
fixes it:

```
! git does not read <tree> as a worktree of <clone> after the rename — repair it: git -C <clone> worktree repair <tree>
```

The rename is not rolled back. A worktree renamed before this release is still unlinked, and
that same command, run from the clone at its new place, relinks it.
