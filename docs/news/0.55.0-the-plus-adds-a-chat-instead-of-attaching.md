version: 0.55.0
headline: The chat bar's `+` adds a chat instead of failing to attach
---

*"trying to add another new session and after pressing `+` getting error: `charter: could
not open another chat — the launcher returned 1`."*

`+` shipped one release ago and could never once have worked. Every press took a branch
meant for a different question and came back with a number.

## What was measured

On the operator's own plane, running the command the press runs, with the stderr the panel
sends to `/dev/null` left on:

```
$ charter frame-new-chat --chat harness-wrapper.1
open terminal failed: not a terminal
✗ charter frame: attaching to the frame failed — `tmux -L charter attach -t $90`
```

No window was made. `tmux -L charter list-windows -t harness-wrapper` — one window, before
and after.

## Why

`cmd_launch` answers "open or focus" (§4k): a launch naming a workspace that is already
open and attached focuses it rather than dragging a second copy into being. The gate:

```python
if not rest and _reopening(args) is None:
    focus = _workspace_to_focus(SOCKET, ws=ws)
```

**A focus is an attach**, and `cmd_new_chat` launches with `attach=False` into the
workspace it is standing in — so the workspace is live and attached *by construction*, the
one state that makes `_workspace_to_focus` answer. Every press focused. In a panel, whose
three streams are all on `/dev/null`, there is no terminal to attach, so tmux refused,
`cmd_launch` handed the refusal back, and the `+` reported it as a launcher failure.

The gate asked `_reopening(args) is None` — which is `_wants_attach` with its first
question missing. `_wants_attach` was split out of that exact expression *because* "am I
restoring" and "am I the terminal" had stopped having one answer, and this site kept
asking the old one. Its own comment records the previous widening: *"And never for a
reopen, which is the same gate one case wider."* `attach=False` is the third case.

```python
if not rest and _wants_attach(args):
```

## What it costs

Nothing else changes. `_wants_attach` returns `_reopening(args) is None` for every caller
that does not pass `attach=False`, so the CLI, `cmd_reopen` and every existing test take
the identical branch — pinned by a control case in the same class, which asserts that a
launch that *is* the terminal still focuses and still makes no window.

## The test that was there

`test_the_launch_does_not_attach` already pinned this — on the wrong side of the seam. It
mocks `cmd_launch`, so it asserts that `+` **asks** not to attach, and nothing asserted
that `cmd_launch` **honours** it. The new cases drive the real `cmd_launch`, and the one
that reproduces the operator's return code makes the fake attach *fail*: with an attach
that succeeds the case is green on the unfixed code too, which is no test at all.
