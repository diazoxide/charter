---
version: 0.62.0
headline: A workspace's baseline is never written through a symlink — a committed link no longer makes `reinit` create a file where it points
security: true
---

**Affected: every release through 0.61.0. Fixed here.** A workspace's tree travels with the
plane, and git stores a symlink as a symlink. When a baseline name in a workspace — its
`refs/README.md`, `workspace.md` or `memory/MEMORY.md` — was a symlink to a path that did not
exist, charter called the file missing and created it through the link. So a link someone
committed made a teammate's `charter workspace reinit`, `restore` or next launch create a file
at a path the committer chose, with the teammate's permissions. The content was always charter's
own baseline text, so this was a write to a place charter did not choose, not a way to put chosen
content anywhere. A `refs` linked to any existing directory got charter's README written into it
the same way, because that write was never containment-checked. Charter's usual containment
refused links out of the plane for the other names, but it did so by ending `reinit` with an
uncaught refusal. It also allowed a link to nowhere that stayed inside the plane.

Every baseline path is now checked without following links. Nothing is written through a link
where a baseline file belongs, wherever it points. A link where a directory belongs is followed
only when it lands on a directory inside the plane's data. That is the repointed `refs` that
this release's `reinit` entry sends you to make. `reinit` exits 0 and names the link and what clears it:

```
! 'north': refs/README.md cannot be created — …/workspaces/north/refs/README.md is a symlink, and charter writes nothing through one; replacing it with a real file clears this.
! 'north': memory/MEMORY.md cannot be created — …/workspaces/north/memory is a symlink, and charter writes nothing through one; replacing it with a real directory clears this.
```

The file itself is created exclusively too. If a link appears between the check and the write,
the operating system refuses the create and nothing is made through it. The workspace's
`.charter-structure` stamp gets the same rule. The containment elsewhere in this release stops
charter writing it through a link out of the plane, but on its own that still followed one that
stayed inside the plane; now the open refuses any link there.

A workspace whose `memory` is a plain file no longer takes `reinit` down with an uncaught
refusal either. It gets the sentence a `refs` file already had: "is not a directory, and charter
never moves existing content; moving it out of the way clears this."

Nothing to adopt. Run `charter workspace reinit --all` to see whether any workspace on your
plane holds such a link ([#1037](https://github.com/diazoxide/charter/issues/1037)).
