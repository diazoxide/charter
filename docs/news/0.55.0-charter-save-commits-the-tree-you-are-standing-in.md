headline: `charter save` refuses from a worktree instead of committing someone else's tree, and every save names the tree it committed
---

*"I ran `charter save` in my worktree. It committed the operator's half-finished
`charter.toml`, and a scratch file I had never opened, under my message — and none of my
own work."*

## What was measured

A throwaway plane, a linked worktree over it, the operator mid-edit in the plane and the
agent's own change sitting in the worktree. `charter save "agent: unrelated security fix"`,
typed in the worktree, on the tree before this change:

```
✓ Committed 7e6c3fe: agent: unrelated security fix  (2 file(s))
 NOTES.txt    | 1 +
 charter.toml | 6 ------
--- the agent's own work, in the worktree ---
?? agent-work.txt
```

Three harms in one call, none of them announced:

1. the operator's **mid-edit** `charter.toml` — a `[[frame.component]]` arrangement deleted
   — committed under the agent's message, on the plane's own branch;
2. an unrelated scratch file the agent had never seen, committed with it;
3. the agent's own work, the only thing it asked to save, **not committed at all**.

Reproduced in both layouts a worktree of a plane is found in: beside the plane, and at
`<plane>/.claude/worktrees/<agent>`, which is the layout `.gitignore`'s own last line says
the harness uses. `git worktree list` on this project's clone showed **22 live worktrees**
while this was being written.

## Why one command could do that

`root._plane_of` sends a linked worktree's plane back to the tree it was cut from, and for
identity that is right: a worktree is a *view of a plane's repo*, not a second plane, so
personas, the vault and memory must not fork per worktree. `charter save` is
`commit_push(config.ROOT, ["add", "-A"], …)` — so from a worktree it ran `git -C <the
plane's clone> add -A` and committed **that** tree.

Every layer above it agreed. The success line was `✓ Committed <sha>: <message>  (N
file(s))`: a sha, a count, and no path. A commit landing in a clone the caller was not
looking at read exactly like a commit landing where they meant.

## What happens now

```
✗ Refusing to stage all of /…/plane — you are standing in /…/plane/.claude/worktrees/agent,
  a linked worktree of it. Committing every change in a tree you are not in would take that
  tree's uncommitted work under your message, and leave your own work here unsaved.
•   your own work:   git -C /…/worktrees/agent add -A && git -C /…/worktrees/agent commit
•   the plane's own: run `charter save` from /…/plane
•   you really do mean this tree: CHARTER_ROOT=/…/worktrees/agent charter save
```

and every save, from anywhere, now names the tree it committed:

```
✓ Committed 0478f61 in /…/plane: operator: save  (2 file(s))
```

That line is the half that would have made this visible months ago, and it is free.

## The guard is on the *add*, not on the command

The property that makes a call dangerous is that it stages files the caller never named
and, from another working tree, cannot see. So the refusal lives in `planegit.commit_push`
where the root and the add meet, keyed on whether the add would stage files it never
named — and the next caller to copy `charter save`'s shape inherits the guard instead of
re-deriving this defect somewhere nobody thought to look.

**Scoped adds from a worktree are deliberately still allowed.** Reactive memory, the
dispatch tally, the workspace manifest and `charter version pin --push` all reach the same
function with an add naming specific plane-state files. Those files belong to the plane and
have no worktree copy that would be right, so refusing them would stop every agent working
in a worktree from recording memory at all — a larger harm than this one, and it would take
`push_head`'s rebase-on-rejection path down with it.

## Detection, and the one that was rejected

The test is `root.tree_of(root)`: pure path arithmetic on the `.git` *file* git writes into
a linked worktree, asking whether the caller is standing in a worktree **of the tree being
committed**.

It is deliberately **not** keyed on `$CHARTER_SESSION_ID` or any other environment variable.
Every agent spawned from a frame inherits that variable — a subagent shell three levels down
still reports the frame's chat id, which is the measurement that sank the same idea in
*"Typing a workspace command no longer moves your chat"* — so a guard keyed on it fires on
processes that are not what anybody meant. Git's own answer is the one that is true about
the directory rather than about the shell.

## `$CHARTER_ROOT` still means "I mean this tree"

`CHARTER_ROOT=<worktree> charter save` is honoured, and commits that worktree — the hatch
`personas/release/memory/` already instructs agents to set for exactly this shape. It falls
out of the detector rather than being an exception bolted onto it: under that override the
tree being committed *is* the caller's own, no ancestor of the working directory is a
worktree of it, and the answer is simply `None`. The harm this refuses — committing a tree
you are not standing in — is not reachable through it, and the refusal names it.

## Verification

Thirty-two new cases in
`tests/test_save_commits_the_tree_you_are_standing_in.py`, over a real git plane with two
real linked worktrees (real git, because the redirect under test is decided by a `.git` file
only git writes), plus an end-to-end run of the real CLI in the harness's own layout.

**The predicate is checked against git, not against what the flags look like they mean.**
The first draft read `git add -A --` as bounded by the separator and bare `git add` as
unbounded; measured, git stages the whole tree for the first and nothing for the second, so
the guard would have waved through the exact call it exists to stop. The unit tests written
from the same belief agreed with it, which is the whole failure mode — so a case now runs
each argv shape in a real repo holding one edited tracked file and one untracked file, and
asserts the predicate against **whether git staged a file the argv never named**. Restoring
the first draft turns it red on all three disagreements, with git's own evidence in the
message.

**And the deletion sweep found a defect in the guard itself, then two more things.** The
predicate asked whether *all* the pathspecs were whole-tree spellings; the sweep offered
`any` and it survived, so no test could tell the two apart. Measured against git, `any` is
the correct one: `git add -- . u.txt` stages the whole tree, because one whole-tree spelling
anywhere in the list widens the call and the named path beside it changes nothing. The
shipped `all` read that as scoped and would have waved it through. Restoring `all` now turns
three cases red.

Its next two survivors were the `--` split itself and a filter beside it, and they were two
different findings. The split is observable in exactly one shape — a file genuinely named
`-A`, which past the separator git stages as a *file* (measured) and which the guard would
otherwise refuse as a whole-tree add — so that case now exists and pins it. The filter was
not underspecified but dead: it narrowed a list that is only ever read when narrowing it
changes nothing, so it is deleted rather than pinned, which is what this repository does with
an equivalent mutant.

Every guard was hand-mutated to confirm it is load-bearing: neutralising the detector turns
11 cases red; making it ignore the add's shape turns the scoped-add case red; moving it to
*after* the `git add` turns the "stages nothing" case red; keying it on "am I in any
worktree" instead of "a worktree of this root" turns the `$CHARTER_ROOT` case red; and
restoring the old success line turns the tree-naming case red.

Two assertions written first did not measure their own guard and were rebuilt rather than
left green: "the agent's work is still untracked in the worktree" is equally true of the
defect, and is now pinned as the pairing that matters — the tree the remedy *names* is the
tree that holds the work; and "the plane's path appears in the output" was satisfied by the
new success line, so the refusal's own return code is now asserted as a precondition.

Closes #806 and #726.
