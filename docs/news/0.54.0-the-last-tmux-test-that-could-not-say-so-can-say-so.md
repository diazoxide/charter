headline: The last tmux test that had to assert where its siblings skip now measures the same thing they do, and the obstacle written down for it turned out not to be its own
---

Charter's tmux integration module has one rule for a death it could not measure: a trial
that says nothing about charter is spent again, and after three of them the test skips
naming what it could not get. On a loaded tmux 3.4 a pane's fd can close before tmux has
the child's status, and for some deaths it never gets it — `#{pane_dead}` `1`,
`#{pane_dead_status}` empty, the pane's `pane-died` array never run, permanently. Measured:
7 of 118.

One test was exempt, and said so in the module's own header: the one that reads the exit
code a whole real `cmd_launch` returns. A void death there came back as
`_UNKNOWN_DEATH_CODE`, which is `1`, and the assertion read

```
AssertionError: Lists differ: [1] != [21]
      : the harness's own exit code did not come back
```

— a red about the runner, in the one test with no way to say so. It happened: `test (3.11)`
went red at a branch head whose *other* workflow run, started two seconds later on the same
image, went green at 3.11, with the test running in both.

## The reason it was exempt was true of a different code path

The header said that pane carries charter's production `pane-died` pair — `[0]` the write
hook, `[1]` `kill-session` — so there was no free index for a probe. That pair belongs to
charter's own private server. This test drives the *operator's tmux* path, whose own
docstring says it installs no hooks on the harness pane at all, because it is awake for the
whole life of the frame and reads the status itself. `show-hooks -p` on that pane during a
real launch confirms it: empty. The index was free the whole time.

What is true of that path is the other half, and it is why the probe still needed something
new: this launcher runs `kill-window` the instant it has the code, so a probe's evidence
written on the dying pane is destroyed microseconds later by the very path under test.

## The evidence moves to the server, and it was checked against the test's own subject first

The probe's action is a tmux command, not a shell command line — #507's point, kept: it is
set by tmux in the same act as running the array, with no shell, no fork and no filesystem
in between, so "the array ran" and "a marker got written" cannot be confused. All that
changes is the option's scope. Measured against tmux 3.7c: a `pane-died` hook whose action
is `set-option -s` fires on the dying pane, and the option survives that `kill-window` and
the frame's whole session.

The test it lives in asserts that a launch writes *nothing* of the operator's tmux, so the
first thing checked was whether the probe could answer that question for it. It cannot: a
server option appears in none of the five readings that test snapshots — `show-options -g`,
the operator's session, `show-options -g -w`, their own window, and `list-keys` — and it is
armed after the snapshot is taken.

## Every other `1` still fails, and each says which one it is

A void is now retried up to three times and only then skipped. Anything else that comes
back `1` is a failure with its own sentence, decided from facts already recorded rather
than from a new guess:

* **the array ran and charter still answered `1`** — tmux had the child's status and the
  code was lost between them. That is the failure this test exists to report.
* **charter recorded no exit for the frame at all** — the harness pane vanished rather than
  dying askably, or the launch returned before the harness ever ran. Both are charter's.

Each of the three outcomes was driven by injecting its own fault and checking the verdict,
rather than waiting for a loaded runner to produce one.
