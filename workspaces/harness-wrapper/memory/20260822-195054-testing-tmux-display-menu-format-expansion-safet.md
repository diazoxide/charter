# Testing tmux display-menu format-expansion safety (the #(...) execution 

_2026-08-22 19:50 · persistent_

Testing tmux display-menu format-expansion safety (the #(...) execution hole) is fragile: (1) display-menu refuses with 'no current client' unless a real client is attached, so needs a pty.fork()-based attach, not just a detached session. (2) Issuing 'tmux display-menu -c <client> ...' DIRECTLY as a CLI command (via subprocess.run or Popen) does NOT reliably trigger the same format-expansion code path as firing the identical command from a key binding (bind -n KEY display-menu ...) -- confirmed by hand: an unescaped #(touch CANARY) label created no canary via direct invocation but did via bind+keypress. Tests must bind the command to a throwaway key and press it through the pty's own fd. (3) tmux send-keys -t <pane> does NOT reach an active menu overlay's key handling (feeds the pane's own input queue instead) -- must os.write() the key directly to the pty master fd. (4) Watch label length: tempfile.mkdtemp() paths on macOS run 55-70+ chars before a filename, which silently truncates a #(...) job embedded in a menu LABEL past any length bound (e.g. a 60-char cap), cutting off the closing ')' and accidentally neutralizing an injection test for the wrong reason -- use short canary paths (e.g. /tmp/short-name) for anything embedded in a label.
