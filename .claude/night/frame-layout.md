## Bypass

No security bypass. I attacked the three guard surfaces the branch touches and every attempt was refused, with the branch strictly stronger than `origin/main` on each.

`_reassert_sizes` / `cmd_resize`, hostile values planted in the frame's on-disk `panes` map: `%1;kill-server`, `%1 ; kill-server`, `%1\nkill-server`, `$(touch /tmp/x)`, the fullwidth `%１１`, the Arabic-Indic `%١٢`, and the space-padded `  %1  ` all produced an empty command list. Only `%1` and `%01` passed, as tmux's own shape. `cmd_resize` fed `{"bottom": "%1;kill-server", "kill-server": "%2", "top": "%3"}` issued exactly one argv — `tmux -L charter resize-pane -t %3 -y 1` — with the hostile value dropped by `_PANE_ID_RE` and the hostile slot NAME dropped by `slot not in _RESIZE_FLAG`. Values reach tmux as argv elements, never as action text, so a `;` is a filename character there anyway.

`_resize_hook_argv`: `demo-1;>/tmp/CANARY`, `a b`, `a\nb`, `../x` and `%1` all returned `None` (nothing armed, one warning); only `[A-Za-z0-9._-]+` armed, and the interpreter path goes through `_action_word_is_safe` exactly as `_panel_died_hook_argv`'s does. No pane id reaches re-parsed action text at all now, where main interpolated a disk-read one on the `_relayout` path.

Weaker-than-main check, surface by surface: `_relayout`'s shape check hoisted above the `want` branch is strictly more refusals (mutation: moving it back below `continue` → RED, 1 failure). `_reassert_sizes`' own check is not redundant (mutation: deleting it → RED, 1 failure). `layout.bottom_rows`' cap is load-bearing (mutation: `max(floor, content_rows)` → RED, 5 failures). `instance.FRAME_SLOTS` is narrowed. `inflight.still_running` returns fewer names, and a pre-#420 record with no `kind` field reads as `DISPATCH` — verified. `inflight.finish` no longer deletes an unparseable record main would have deleted; that is a refusal, not a weakening, and `live_records` already skips it on the way to every reader. `_pairs`/`_hits` widened from `== 3` to `>= 3` fields is parse tolerance for charter's own fourth field, with `int()` still gating every value; I confirmed `_hits` reads position 2 (not "the last field", which is now the context percentage) and `_last_ctx_of` swallows an empty ctx field rather than raising. `layout.CARRIABLE`/`_env_argv` untouched.

## Blocking

### 1

(A) `bottom` is sized for a table it then refuses to draw on any terminal 51-94 columns wide, leaving up to 14 blank rows taken from the harness. `slots.bottom_rows_wanted` never looks at the pane width, but `_table_lines` returns `[]` when `width < statusline._LEFT_W` (95). `layout.visible_slots` only drops `right` at `min_cols` (100) and drops everything at `min_cols // 2` (50) — so `bottom` is drawn, and content-sized, all the way down to 51 columns. Reproduced on a `git archive` extraction of the branch: with 6 repos cached, `bottom_rows_wanted` = 7 and `layout.bottom_rows(content_rows=7, window_rows=40, slots=['top','bottom'])` = 7; rendering `slots.render('bottom', fid)` into a 7-row pane gives 7 lines at cols=200/100/95 and exactly 1 line ('0 todos · F2 menu') at cols=94/80/60. On main `bottom` was one row at every width, so this is a regression the operator hits by narrowing their terminal below 95 columns — and `cmd_resize` re-applies it on every subsequent resize, because `_reassert_sizes` computes `content_rows=frame_slots.bottom_rows_wanted(fid)` with no width either. Worst case is not cosmetic: in a 26-row / 80-column window with 14 repos, cap = 26-2-1-12 = 11, so `bottom` takes 11 rows to draw 1 line and the harness is pinned at its `HARNESS_MIN_ROWS` floor of 12 — roughly half the terminal blank. Fix: `bottom_rows_wanted` (or `layout.slot_sizes`) has to take the width and return `SLOT_SIZE['bottom']` below `statusline._LEFT_W`. Both launch sites (`commands_frame.py:1496`, `:2055`) and `cmd_density` (`:2641`) already have `cols`; `cmd_resize` (`:2581`) computes it and throws it away as `_cols`. Files: /Users/aharon/IdeaProjects/charter (branch `frame-layout-488`) charter/frame/slots.py `bottom_rows_wanted` / `_table_lines`, charter/frame/layout.py `bottom_rows`, charter/commands_frame.py `_launch_sizes` / `_reassert_sizes`.

### 2

(A) The same seam breaks a second, independent way at `minimal` density, on a full-width terminal. `_bottom` applies `budget = min(_height() - 1, _TERSE_ROWS)` when `verbosity(fid) == 'terse'`, but `bottom_rows_wanted` does not read the density at all. Reproduced with 10 repos and `state.record_density(fid, 'minimal')` at cols=200: `bottom_rows_wanted` returns 11, the renderer fills 5 (attention row + 3 repo rows + `…(+7 more, all clean)`), so 6 rows of the pane are blank. This is worse than the width case because `minimal` is a shipped level the F2 menu offers, and `instance.FRAME_DENSITY` documents it as "For a terminal where the harness's own rows are what you came for" — as shipped it hands the harness *fewer* rows than `normal` would have been worth, and shows less in them. It is reached both at launch (`_launch_sizes`) and by the live re-layout (`_relayout` → `_reassert_sizes`), neither of which threads verbosity in. Fix alongside the width: `bottom_rows_wanted` must apply the same `_TERSE_ROWS` cap the renderer applies, so the launcher and the renderer are still one answer. File: charter/frame/slots.py `bottom_rows_wanted` vs `_bottom` (the `if verbosity(fid) == 'terse': budget = min(budget, _TERSE_ROWS)` branch).

### 3
