headline: Two tmux tests stop reporting the runner's bad luck as charter's defect
---

`tests/test_frame_tmux_integration.py` failed twice in one day on CI, in two different
tests, and both times the message named charter (#694). One of them failed on a
`pull_request` run at the same sha whose `push` run had passed — identical code, identical
interpreter. Both messages were wrong about whose defect it was, and each cost somebody an
hour proving that.

They are **two unrelated defects wearing one issue number**, and neither is in charter.

**`_HOOK_TRIALS` is a retry for a trial that measured nothing** — on a loaded tmux 3.4,
roughly one death in seventeen closes the pane's fd before tmux has the child's status, so
the death reports nothing and the pane's `pane-died` array never runs (#487). Nothing about
charter can be read off such a trial, so it is spent again on a fresh pane. Both of these
tests have that loop. Neither could survive entering it.

**`test_the_last_chats_teardown_still_ends_the_session` re-used one workspace name.** Every
trial opened `wsdemo` with `new-session -s wsdemo`, and the *only* state that reaches the
retry is that session still standing — which is exactly the state in which `new-session`
refuses: `duplicate session: wsdemo`, rc 1, reported by the fixture as charter declining to
open a chat. A trial that cannot run twice is not a retry, it is a second way to fail. Each
trial now gets a workspace of its own, and the tmux fact the shape rests on is measured
rather than assumed — `new-session` on a held name does not join, adopt or replace, on
tmux 3.7c and on tmux 3.2 alike.

**`test_nothing_of_the_operators_tmux_is_written_by_a_whole_launch` asked for state the
launch deletes.** It told a void apart from a real defect by reading `state.exit_code(fid)`
back after `cmd_launch` returned — but the last two things a launch inside an operator's
tmux does are give up its claim and run its own closing reap, and that reap's whole job is
to remove the frame the launch just finished. Traced on the green path:
`record_exit('demo.1', 21)`, then `reap` returning `['demo.1']`, then `exit_code('demo.1')`
answering `None`. So the classifier could only ever say "charter recorded nothing", and it
sits on the branch only a void reaches — invisible on an idle machine, and a failure the
first time it ran. It now watches charter record the code instead of reading back a
directory charter has deleted.

Measured, one void injected into the first trial and a real death after it, both worktrees
run at once: `main` failed **50 of 50** on tmux 3.7c and **20 of 20** on tmux 3.2; this
branch **0 of 50** and **0 of 20**. No `sleep` was added to either; nothing here waits for
anything.

The launch's own `state.record_exit` turned out to have had no test behind it: deleted from
`charter/commands_frame.py`, all 8930 tests still passed on `main`. It is pinned now.

Nothing to adopt — no production behaviour changed.
