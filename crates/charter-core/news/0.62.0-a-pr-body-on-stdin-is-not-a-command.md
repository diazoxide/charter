version: 0.62.0
headline: `gh pr create --body-file - <<'EOF'` is no longer refused as a vault read for a body that reads no vault
---

The vault guard read the body of `gh pr create --body-file - <<'EOF'` as commands, because `gh`
is not a program that prints files. In a call like
`gh pr create --title "…" --body-file - <<'EOF' | tail -1`, one apostrophe in the body
(`program's`) made the call unreadable to the guard. Each word of the body then counted as a
file for `tail -1`. Two neighbouring words, "`~`." and "Charter", joined into `.Charter`, which
the guard matches as charter's own directory, and the call was refused with "reads a
vault/secret file directly". A body that named where charter keeps its vaults beside an
apostrophe was refused the same way. The same body fed to `cat` went through.

The quoted body of `gh pr create`, `gh pr comment`, `gh issue create` or `gh issue comment`
given `--body-file -`, `--body-file=-`, `-F -` or `-F-` is now data, on the terms a
`git commit -F -` message gets in this release. It stays visible to the guard when the heredoc is
unquoted, because a `$( … )` in it runs; when a shell is anywhere in its pipeline (`… | bash`);
and when the command asks for the editor (`-e`, `--editor`, `-de`). Other spellings, such as
`gh pr edit`, `gh release create -F -` or a body file that is not stdin, keep the body visible
as before.

A PR title holding escaped backticks, as in `` --title "keeps its \`~/\`" ``, no longer stops the
guard reading the line either. An unescaped backtick is a command substitution and still does.

Nothing to adopt; the guard updates with the plugin
([#1070](https://github.com/diazoxide/charter-plane/issues/1070)).
