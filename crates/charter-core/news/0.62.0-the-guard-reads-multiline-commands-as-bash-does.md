headline: The vault guard reads a multi-line command's newlines, quotes and comments as bash does, closing three reads it allowed
---

**Affected: every release with the vault guard, through 0.61.0.** The Bash vault guard reads a
command line by line to find a `cat <vault>` and refuse it. Three ways its reading of a
multi-line command diverged from bash each let a vault read slip through. All three name the same
cause — the guard's line, quote and comment boundaries were not bash's — and each was measured
against real bash and zsh with a fabricated vault.

- When a command could not be tokenised (one unbalanced quote anywhere is enough — a trailing
  `echo "`), the guard split it on whitespace, which erases newlines. Every line then folded into
  the one before it, so a `cat x.json` on the line after a `cd .charter/vaults` was read as an
  argument of `cd` and never seen as a read ([#1082](https://github.com/diazoxide/charter/issues/1082)).
- A `<<` inside a quoted string that spans lines was read as a heredoc opener, so the lines after
  it — which bash runs as commands — were dropped as heredoc body
  ([#1086](https://github.com/diazoxide/charter/issues/1086) class 1).
- A comment line ending in a backslash was folded into the next line. Bash does not continue a
  comment, so the guard ended a heredoc body a line early and stripped the real read after the
  terminator (#1086 class 2).

The guard now cuts a command on the newlines bash makes a boundary — not one inside a quote it has
not closed, not one a live backslash spliced away, not one following a comment — and lexes each
resulting line on its own, so a broken quote on one line no longer blinds the guard to the
well-formed lines around it. A `<<` carried inside a multi-line quote opens no heredoc.

The two over-corrections an adversarial review warned against stay closed: a newline INSIDE a
quote is still not a boundary, so `grep -e "a\nb" x.json` keeps its operand and is refused;
and the `$( … )` splice is still applied on the unparseable path.

Correct parsing surfaces some commands that were refused only as a side effect of the old
misparse and whose read is a documented **known-open** construct — a quoted `"$(cat <vault>)"`, a
`$VAR`, a glob, an `sh -c '…'` string — allowed on well-formed input and unchanged here. Those
limits are stated in `docs/hooks.md`; this change does not narrow them.

Nothing to adopt; the guard updates with the plugin.
