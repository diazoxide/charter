version: 0.55.0
headline: A chat stays in the workspace it was opened in, instead of being stranded between two
---

*"`F2 → workspace → gamma` in one of my two chats. Now the other one is the only chat either
terminal can see, `charter frame-chat alpha.1` says `no chat 'alpha.1' here`, and tmux's own
window key lands me on a pane with no frame around it at all."*

`F2 → workspace` moved a **chat** between workspaces, and a chat is the one thing in charter
that cannot be moved. Its id is `<workspace>.<n>`; the harness inside it has that workspace's
directory as its cwd, that workspace's files open, and that workspace's work in its history.
Charter re-pointed the label and moved none of that — it calls `move-window` nowhere, so the
tmux window stayed in the session it started in — and the chat ended up listed in a workspace
whose other chats it could not reach, and missing from the one it was actually running in.

Both directions of that were filed. **#733**, backward: the chats it left behind could never
see it again, so a live window of the session on your screen had no palette route, no
`frame-chat` route, and no panels if you reached it with tmux's own key. **#788**, forward:
the other workspace's chats were drawn on its bar, the bar's pre-flight approved every one of
them, and pressing one was refused every time — because their windows are in a different tmux
session and `select-window` cannot cross one.

**The rule was settled before the code was written**, on 2026-08-26, and the code predates it
by a day: *"a chat belongs to its workspace for life; `{workspace}-{hash}` is identity, not a
property."* At the time a frame **was** a workspace, one to one, and moving one was coherent.
The chat tabs that arrived after it made a frame a *chat*, and "moves the frame" quietly
became "moves the chat".

**So the workspace row refuses, and it names the thing that works:**

```
  workspace: alpha — pick another   cannot switch: a chat belongs to its workspace for life
                                    — open a chat in another workspace with
                                    `charter <harness> --workspace <name>`
```

The sentence is on the row *before* you press it and on your own screen if you press it
anyway, from one constant, so the two cannot come to disagree. The workspaces are still
listed and the one you are in is still marked — that row is where you look to answer "which
workspace is this chat in" — you just cannot press one into a move. `charter frame-switch
--workspace <name>` gives the same sentence, and so does a click on a `workspaces` tab.

**Opening a chat in the other workspace is the answer, not a workaround.** It is what the
rule says to do: a conversation wanted elsewhere is a new one, with the right cwd and its own
history. Attaching a client to a workspace you already have open is a different feature —
tmux's `switch-client` — and charter makes that call nowhere yet.

**The launch prompt's lock now names the escape it actually has.** Picking a workspace at
launch locks the session to it, and the line that said so offered `F2 → workspace` first. That
route is gone; `charter workspace unlock`, in the frame's own shell, was always the one that
does the work and is now what the sentence leads with.

**One unreleased change is withdrawn with it.** A workspace switch used to re-size the repo
strip for the arriving workspace's clone count; with no arriving workspace there is nothing to
re-size, and the code went with the switch. `charter frame-resize` and the `window-resized`
hook are untouched — a terminal drag still re-computes every pane height from the frame's
current content.

**Nothing about `charter workspace use` changed.** Typed at the agent inside a frame it still
selects a workspace for that session and still moves the panels; what it never did, and still
does not do, is move the tmux window the harness is running in.
