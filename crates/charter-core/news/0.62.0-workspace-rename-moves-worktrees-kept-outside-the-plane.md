---
version: 0.62.0
headline: `charter workspace rename` moves the worktrees a plane keeps outside `workspaces/`, or refuses before it moves anything
---

With `[plane] worktrees` or `$CHARTER_WORKTREES` set, a piece lives at
`<root>/<workspace>/<repo>/<piece>`. `charter workspace rename` moved `workspaces/<old>` and
left every piece at `<root>/<old>/…`. Everything that looks a piece up by workspace name looks
under `<root>/<new>/`, so after the rename `charter wt list` found none of them, and the next
`charter wt add` in the renamed workspace made a second worktree beside the first.

Now the rename moves `<root>/<old>` to `<root>/<new>` as well, and relinks the pieces at their
new paths. Pieces still under `workspaces/<old>/.worktrees/` from before the root was set move
with the workspace as they always did, and they are relinked too.

Before it moves either directory, the rename checks that both `workspaces/<new>` and
`<root>/<new>` are free. If either one is taken, nothing moves:

```
✗ <root>/<new> already exists, and it is where the worktrees of a workspace named '<new>' live — pick another name or move it first; nothing was renamed.
```

If the workspace moved and the directory under the root could not, the rename is not undone.
Charter prints no ✓ and exits 1. It names the directory it left behind, gives the OS's reason,
and prints the command that finishes the rename:

```
! Renamed workspace '<old>' → '<new>' (clones, memory, and manifest moved), but not its worktrees: <root>/<old> is still at the old name (Cross-device link).
! Finish the rename: mv <root>/<old> <root>/<new> && git -C <clone> worktree repair <root>/<new>/<repo>/<piece>
```

A workspace renamed before this release still has its pieces at `<root>/<old>`. If nothing is
at `<root>/<new>` yet, move that directory there by hand, then run
`git -C <clone> worktree repair <new path>` for each piece in it.
