headline: In a checkout, `charter doctor`'s handoff gate row names `charter workspace reinit` for a rule the plane holds only in its local settings
---

When the plane holds the `ask` rule for `charter handoff *` only in `.claude/settings.local.json`,
the `handoff gate` row gave two wrong hints inside a checkout that had not been given a copy yet:

- At the checkout's root it said `Add it: charter guard ask 'charter handoff *'`. That writes the
  rule into the plane's shared `.claude/settings.json`, which changes the settings of everyone
  on the plane's repository, when you had chosen a local rule.
- In a directory deeper inside the checkout it said the rule `cannot be put in force` for a chat
  rooted there. `charter workspace reinit` writes the checkout's own local file, and Claude Code
  reads that file at the git root for a chat anywhere inside the checkout.

Both now say:

```
The plane's local settings already hold it for claude-code, so this checkout's copy of them is behind — nothing to add, only to refresh: charter workspace reinit <workspace>
```

The row decides from which file `reinit` carries into which directory: the shared file into
workspace directories and checkouts, the local file into checkouts only. So a workspace directory
is never sent to `reinit` for a local rule, and deep inside a checkout a rule the plane holds only
in its shared file is still reported as one no file charter writes can put in force there.

Nothing to adopt ([#1031](https://github.com/diazoxide/charter/issues/1031)).
